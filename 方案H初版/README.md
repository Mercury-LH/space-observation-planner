# 方案H初版：拉格朗日价格协调 + 多方案统一对比

本目录包含两部分：

1. **新算法 H（价格协调）**：给每个站点每 30 秒时间格定价，每颗目标按价格独立挑选最划算的观测，被争抢的时段自动涨价，迭代后用"价值 − 价格"引导放置，再做局部搜索。
2. **统一对比平台**：在同一份窗口、同一套规则、同一个 Skyfield 独立校验器下，重新实现并对比规划方案中的 A–G，用于回答"哪种方案更好"。

## 评委运行指南

Windows、macOS（Apple 芯片）、Linux 都能直接运行，也可以用 Docker。命令都在 `方案H初版/` 目录下执行；赛题数据（仓库根目录的 `data/数据.zip`、`data/优先级.zip`）已随仓库提供。

**环境要求**

- 64 位 Windows 10/11、macOS 12 以上（Apple 芯片）或 Linux（glibc 2.28 以上，如 Ubuntu 20.04+）。Intel 芯片的 Mac 请用 Docker（numba 0.68 没有 Intel Mac 的安装包）。
- 内存建议 16 GB，8 GB 也能跑：规划峰值约 4 GB，Skyfield 逐秒校验分块计算后峰值约 1.6 GB。磁盘约 1 GB。
- 第一次运行要联网（安装依赖；第一次校验时下载 17 MB 的 DE421 星历），之后可以离线。
- 安装 [uv](https://docs.astral.sh/uv/)，它会自动准备 Python 3.12 和 `uv.lock` 锁定版本的依赖：
  Windows 在 PowerShell 里运行 `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`；
  macOS / Linux 运行 `curl -LsSf https://astral.sh/uv/install.sh | sh`；已有 Python 时也可以 `pip install uv`。

**一键启动**（安装依赖 → 准备可见窗口 → 自动打开浏览器 http://localhost:8501）：Windows 双击 `start_app.bat`，macOS 双击 `start_app.command`，Linux 运行 `bash start_app.sh`。

**三条命令**

```bash
uv sync --extra app                                    # 安装 Python 3.12 和依赖
uv run python -m obsplan plan --mode fast --validate   # 全量规划 + Skyfield 逐秒校验，结果写到 outputs/plan/
uv run streamlit run app/streamlit_app.py              # 网页界面：浏览器打开 http://localhost:8501
```

`outputs/plan/` 里是 `plan.csv`（观测计划，含 Skyfield 复核的仰角和太阳角）、`target_status.csv`（每颗目标的观测情况）和 `summary.json`（指标、用时、校验结果）。快速模式应得到覆盖 9987 颗、得分 28237.8、任务 12097 个，Skyfield 校验全部合法；同一台机器上重复运行，结果逐字节相同。

**Docker**（在仓库根目录执行，不用装 uv）

```bash
docker build -f 方案H初版/Dockerfile -t obsplan .
docker run --rm -p 127.0.0.1:8501:8501 obsplan        # 网页界面：浏览器打开 http://localhost:8501
docker run --rm -v "$PWD/out:/out" obsplan python -m obsplan plan --mode fast --validate --out /out/plan
```

结果写到当前目录的 `out/plan/`（Windows 命令提示符里把 `$PWD` 换成 `%cd%`）。构建时已算好默认规则的可见窗口、取好星历、编译好 numba 函数，容器里的规划不用再等这几步。Docker Desktop 的内存上限（Settings → Resources）建议 6 GB 以上，否则规划可能被系统终止（退出码 137）。

**预计用时**（10 核 M1 Pro、16 GB 实测；核数少的电脑相应变慢）

| 步骤 | 第一次 | 之后 |
|---|---:|---:|
| 安装依赖 | 1–5 分钟（看网速） | 几秒 |
| 计算可见窗口（多进程） | 约 20–30 秒 | 读缓存 |
| 快速模式规划（含按秒精修） | 约 100 秒（含 numba 首次编译约 25 秒） | 约 75 秒 |
| Skyfield 逐秒校验（约 1.2 万个任务） | 约 100 秒（含下载星历） | 约 90 秒 |
| 上面第二条命令合计 | 约 4 分钟 | 约 3 分钟 |

Docker 首次构建除下载依赖外，预先计算约 1–2 分钟。

**常见问题**

- **提示找不到 uv**：按上面的方法安装，装完关掉终端（命令行窗口）再重新打开。
- **国内网络下载慢**：先设置 PyPI 镜像再运行，uv 会把 `uv.lock` 里的下载地址换成镜像，版本不变。Windows 命令提示符：`set UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple`；macOS / Linux：`export UV_DEFAULT_INDEX=https://pypi.tuna.tsinghua.edu.cn/simple`。电脑上已有 Python 3.12 时 uv 直接用它，不再下载 Python。Docker 构建时加 `--build-arg PIP_INDEX_URL=镜像地址 --build-arg UV_DEFAULT_INDEX=镜像地址`。
- **星历下载失败**：程序先从 JPL 官网下载，失败再从 PyPI 的 skyfield-data 包里取同一文件，都核对 SHA-256。都不通时，在能上网的电脑上下载 https://ssd.jpl.nasa.gov/ftp/eph/planets/bsp/de421.bsp ，放到 `方案H初版/cache/de421.bsp`。只规划、不校验时用不到星历。
- **8501 端口被占用**：命令后面加 `--server.port 8502`，一键脚本同样可以加（如 `start_app.bat --server.port 8502`）。
- **Windows 提示"已保护你的电脑"**：点"更多信息 → 仍要运行"。**macOS 提示无法打开 `start_app.command`**：右键 → 打开，或在终端运行 `bash start_app.command`。
- **内存不足、进程被终止**：规划峰值约 4 GB，关掉其他大程序再试；用 Docker 时调高内存上限。
- **路径里有中文或空格**：支持，已在这样的目录里测试过。Windows 上若安装依赖时报路径过长，把整个目录移到较短的路径（如 `C:\obsplan`）。
- **界面第一次"运行规划"**：要先算可见窗口（约半分钟，一键脚本已提前算好），全量快速模式约 1–2 分钟出结果；左侧"演示模式"缩小规模，几秒出结果。

## 规则口径（依据答疑文档，均可在 `obsplan/config.py` 修改）

| 项目 | 取值 | 依据 |
|---|---|---|
| 规划期 | **2026-08-01 00:00 至 08-07 00:00 UTC**（TLE 历元约 8 月 3 日） | 企业老师 2026-10-21 群内确认（取代答疑 #26 的 10 月写法）；时间制见答疑 #42 |
| 仰角 | 全程 10°–85° | 站址文件、答疑 #26 |
| 站点太阳高度角 | 全程 < −6° | 答疑 #26（−6° 为建议值） |
| 目标受照 | 全程不在地球影子内（与 Skyfield `is_sunlit` 同一球形地球模型） | 答疑 #26、#36、#44 |
| 观测时长 | 120–240 秒，60%→100% 线性计分 | 答疑 #30 |
| 切换 | 30 秒；每站同一时刻只观测一个目标 | 说明.docx、答疑 #26 |
| 重复观测 | 上次观测结束 48 小时后可再次计分 | 答疑 #30、#32 |
| 计分 | 覆盖数、总得分两项独立计分 | 答疑 #36 |

**开发假设**：两项独立计分的换算公式尚未公布（答疑 #48），对比时采用
`综合 = 0.5 × 覆盖数/10000 + 0.5 × 得分/30062`（30062 = 每颗目标满分观测一次的总分），仅作内部比较口径，不是比赛成绩。

## 运行

```bash
uv sync
uv run python -m obsplan plan --mode fast --validate      # 规划 + Skyfield 校验，输出 plan.csv、target_status.csv 与 summary.json
uv run python -m obsplan validate 某个计划.csv             # 复核任何人的计划（含目标受照、48 小时、切换时间）
uv run python -m obsplan status 某个计划.csv               # 目标状态分析：每颗目标观测几次、时长、未覆盖原因
uv run python run_compare.py                              # A–H 全部方案统一对比（--add-evolved 只补 H+ 两行）
```

`plan` 的选项：`--mode fast|quality`、`--start 2026-10-01`（换规划期）、`--moon 30`（月光规避）、`--weather`（按历史晴空概率规划）、`--manual-rule`（放置规则只用人工的"价值 − 价格"）、`--rule-only`（只用伐谋演化的规则）。默认是稳健模式：两条规则各排一份，取综合高的，用时只多 1–6 秒，见"泛化检验"。

**目标状态分析**（`obsplan/target_status.py`；答疑 #26：赛题中的"目标状态分析"按观测任务状态理解）：`target_status.csv` 每颗目标一行——状态（外推异常 / 无可见窗口 / 未覆盖 / 已观测 1–3 次）、观测次数与理论最多次数、总观测秒数、得分、首次与最近一次观测时间、所用站点、可见窗口数，以及未覆盖或未观测满的原因；只计满足 48 小时间隔的观测，与计分口径相同。`summary.json` 里有按优先级、轨道类别的汇总，界面"概览"页可按状态查看明细并下载。默认流水线（H+）的结果：可观测 9999 颗中覆盖 9994 颗，高优先级 2023/2024（另 1 颗外推异常），观测 2 次以上的目标 1684 颗；未覆盖的 5 颗都是低优先级低轨目标，可见窗口的站点时间都已被占满。融合模式 9999 颗全部覆盖（汇总见 `results/target_status_*.json`）。
`validate` 能读本方案导出的 CSV、方案G初版的 `schedule.csv`（列 station_id、target_id、start、end），以及观测列表 JSON（方案E初版的格式；时间是相对规划开始的秒数时加 `--seconds-from-start`）。

数据在仓库根目录 `data/`：`数据.zip`、`优先级.zip` 已随仓库提交，程序直接读取；换成解压后的 `轨道.txt`、`站址.txt`、`高/中/低优先级目标.txt` 也可以。
测试：`uv run pytest -q`（82 个，约 40 秒；`-m "not slow"` 跳过 Skyfield 逐秒校验测试）。

首次运行会计算可见窗口（M1 Pro 约 30 秒）并缓存，Skyfield 校验会自动下载 DE421 星历（约 17MB，JPL 取不到时改从 PyPI 取同一文件）到 `cache/`。
完整对比（含 CP-SAT 约 9 分钟、11 份计划约 12.7 万个任务的 Skyfield 逐秒校验约 17 分钟）约 30 分钟。

- **规划期改为 8 月后，问题的性质变了**：离 TLE 历元只有 ±3 天，9999 颗目标都可观测（只有 1 颗外推失败）；北半球夏季夜短，站点黑夜共 588 小时（原 10 月口径为 668 小时），4 号站 6 天只有约 37 小时。覆盖已接近饱和，得分主要靠"48 小时后再看一次"的重复观测。
- **伐谋演化的放置规则让默认流水线提高 0.8%**：价格协调收敛后按什么顺序放置候选，原来是人工的"价值 − 价格"，现在用伐谋演化并已采纳的规则（`obsplan/evolved/recover_rule.py`，实验记录见 `integrations/famou_h/README.md`）：覆盖 9987 → 9994，得分 28084 → 28538，综合 0.966 → 0.974，用时多约 15 秒，超过了要 9 分钟的 G+。命令行加 `--manual-rule`、界面关掉开关可退回人工规则。
- **三份计划合并后再求解最好（0.978）**：H+、G+、E 选中的任务差别很大（三份完全相同的任务只有 22 个），合并成候选池用 CP-SAT 重解，9999 颗可观测目标全部排上，比 H+ 高 0.4%；只用 H+ 自己重解约 6 分钟就到 0.976。见下文"多方案解合并"。
- **采用伐谋规则之前，单个方案里质量最高的是 G+（CP-SAT 分块 + 同一套局部搜索 + 按秒精修），但要 9 分钟；H 只用约 100 秒，达到它 99.8% 的综合指标**。差别在重复观测：CP-SAT 在每个 4 小时块里把 120 秒任务排得很紧（G+ 有 86.5% 的任务是 120 秒、重复观测 3105 次），H 的价格协调更偏向延长观测（120 秒任务 73.8%、重复观测 2519 次）。试过让 H 构造阶段只排 120 秒（0.950，重复观测挤占覆盖）、加大局部搜索力度（无提升）、局部搜索跑两遍（+0.0007，多 54 秒）、在 H 计划上做 240 秒 CP-SAT 分段重排（+0.0005）、把 H 的计划作为 CP-SAT 分块的初始提示（0.966，没有超过 H），都不值得；CP-SAT 每块限时 5 秒（总 279 秒）时 0.9668，2 秒时找不到可行解。
- **多给时间还能更好（0.990）**：在最好计划上不断生成新计划再合并（长跑优化），约 4.5 小时到 9999 颗 / 29474 分 / 综合 0.9902，约 7.6 小时到 29485 分 / 0.9904，见下文"长跑优化"。
- **长跑之后再提 0.5%（0.9952）**：按秒跨站弹射链成批加入高优先级重复观测，约 50 分钟从 0.9907 到 9999 颗 / 29778 分 / 综合 0.9952；同时把按秒口径的上界从 1.0058 收紧到 1.0047，离最优最多差 0.94%。见下文"按秒跨站弹射链"。
- **离最优最多还差多少**：可证明的上界（任何合法计划的综合指标都超不过它）在 30 秒格点口径下是 1.0027，在按秒口径下是 1.0058（对按秒精修后的最终计划也成立）。默认流水线（0.974）离最优最多差 3.1%，融合模式（0.978）最多 2.8%，长跑优化（0.990）最多 1.5%。见下文"离最优还有多远"。
- G 用多线程 CP-SAT，每次运行结果略有波动；其余方案可复现。
- 机器为 Apple M1 Pro（10 核），用时含 GA 训练，不含窗口预处理与校验。`results/compare.json` 为机器可读结果，计划明细 CSV 含目标编号，未提交。10 月口径（规划期确认前）的全部结果保存在 `results/oct_period/`。

### 按秒精修（`obsplan/refine.py`）

30 秒网格上，窗口首、末采样点之外往往还有 0–29 秒是真正可见的，网格计划用不上。精修在网格计划之后做两步：
1. 对每个任务所在的窗口，两端按 1 秒逐点检查全部条件（仰角、太阳角、目标受照、月光、外推合理性，余量与窗口计算相同），得到真实可见区间；
2. 任务集合和先后顺序不变，解一个线性规划（OR-Tools GLOP）：最大化 Σ 优先级 × 观测时长，约束为任务落在真实可见区间内、时长 120–240 秒、同站相邻任务之间留 30 秒切换、同一目标相邻两次观测间隔 48 小时。约束都是"两个变量之差 ≤ 整数"的形式，最优解自然落在整秒上。

全量约 4 秒，对三种方案都有效：H 得分 27359 → 28084（+2.6%），E +2.3%，G+ +1.5%（G+ 的任务多为 120 秒、排得更紧，可延长的余地小）。命令行和界面默认开启（`--no-refine` 关闭）。

**按秒补覆盖**：只在网格上看不见、按秒才有满 120 秒窗口的目标，精修前先插进站点时间线：同站任务允许压到 120 秒、在各自真实窗口内前后移动（正向、反向两遍推算判断能否腾出位置），腾不出时可删掉一到两个价值更低的重复观测；线性规划不可行就逐个撤回，插入后综合变差就整体放弃。8 月口径下所有目标在网格上都已可见，这一步没有候选；在原 10 月口径下有 45 颗这样的目标（7 颗高优），插进了 9 颗。只往空闲时间里插（不压缩、不删除）一颗都插不进去：原 10 月口径的网格计划里 92.5% 的同站相邻任务正好只隔 30 秒切换。

### 多方案解合并（`obsplan/fusion_merge.py`，融合模式）

`uv run python scripts/fusion_merge.py`（先要有 `results/plan_H+.csv`、`plan_G+.csv`、`plan_E.csv`，即 `run_compare.py` 与 `run_compare.py --add-evolved` 的输出；结果 `results/fusion_merge.json`）。

1. **建池**：H+、G+、E 三份网格计划共 37374 个不同的任务（站点、目标、开始、时长都相同才算同一个），三份都选中的只有 22 个。每个任务再补同一窗口内 4–8 格（120–240 秒）的左对齐、右对齐版本和前后平移 1 格的版本，第一轮池中 383433 个候选。
2. **建模**：候选开始时间固定，站点占用（含 30 秒切换）和同一目标 48 小时间隔都是区间相交；扫描线求出区间图的全部极大团，每个团一条 AtMostOne，精确且线性松弛紧。目标函数的整数系数与综合指标严格成比例（覆盖奖励 sumP，任务 P×(2000+1000m)）。
3. **求解**：24 小时一块、每次前移 12 小时滚动，块外固定、块内重排，变好才接受（每块不到 1 秒解到最优）；之后局部搜索。局部搜索的结果加入池中再合并一轮，共 3 轮；最后按秒精修。

| 阶段 | 覆盖 | 得分 | 综合 |
|---|---:|---:|---:|
| 输入：H+ 网格计划（提示，三份中综合最高） | 9994 | 28013 | 0.9656 |

### 按秒跨站弹射链：长跑之后再提 0.5%（`obsplan/chain.py`、`scripts/chain_run.py`）

长跑到 0.9906 之后每轮只涨 0.00001～0.0001。看计划的构成就明白原因：10 个站的黑夜时间已经 100% 用满，低、中优先级目标基本都只观测一次 120 秒，多出来的时间全花在高优先级任务的"延长"上。同样的 150 秒，用来延长高优先级任务值 2.5 分，用来给另一颗高优先级目标多做一次观测（120 秒 + 30 秒切换）值 3 分——**每换成一次只涨 0.5 分（综合 +0.000008），但能换的有上千次**。难点是新观测只能放在它自己的可见窗口里，那里通常已经被别的任务占着。

做法和"二分图匹配里找增广路"是一个思路，全部按秒、可以跨站跨夜晚：

1. 每个"站 × 夜晚"是一条时间线，任务顺序固定。把全部任务压到 120 秒，前向算每个任务最早结束、后向算最晚开始，于是"这个空当里再塞一个任务行不行""拿掉某个任务后行不行"都是瞬间能判断的。
2. 对一颗还没观测满 3 次的高优先级目标做广度优先搜索：它的某个窗口能直接挤进去就成功；否则顶掉那里的任务 X，X 去它自己的其他窗口（别的站、别的夜晚）找位置，还不行就再顶掉 Y……被顶掉的如果是优先级更低的重复观测就直接删掉。
3. 找到一条链后，对涉及的几条时间线解一次线性规划重新定起止时间，总分变高才接受；不划算就禁用丢分最多的那一步再搜。
4. **重排节奏**：还缺观测的高优先级目标里，四成多按现有两次观测的时间根本放不下第三次（比如第 1 天、第 4 天各一次，哪里都凑不出 48 小时间隔）。这时把其中一次挪到别的窗口、再补第三次，三步作为一个整体，总分变高才保留。

|---|---|---|---|
| 起点：长跑最好计划 | 0.9907 | 12726 | — |
| 弹射链，最多连顶 2 个任务 | 0.9930 | 12998 | 7 秒 |
| 加错位插入、删低价值重复、失败重试，最多连顶 4 个 | 0.9942 | 13133 | 4.5 分钟 |
| 最多连顶 8 个 | 0.9947 | 13194 | 32 分钟（单线程） |
| **再加重排节奏** | **0.9952** | 13224 | 再 14 分钟（单线程） |

（前三行在本机从 0.990643 那份出发；后两行在服务器上从多一次观测的 0.990665 那份出发。）

- 最终 9999 颗 / 29777.8 分 / **综合 0.995223**，Skyfield 逐秒校验 13224 个任务全部合法，`structural_violations(by_second=True)` 无违规。观测满 3 次的高优先级目标从 896 颗增加到 1275 颗。汇总见 `results/chain.json`。

- 把"网格上不够 120 秒、按秒才够"的 1.1 万个短窗口也作为候选（`--short`）还能到 0.99528，但这类窗口不在常规窗口表里，结构检查要带上额外窗口，也还没做 Skyfield 校验，没有采用。
- **更紧的按秒上界（`obsplan/second_dual.py`、`scripts/second_dual_bound.py`）**：原来的按秒上界把每个窗口两端各放宽 30 秒，而真实能多用的平均只有 14 秒。改用每个窗口逐秒探查出的真实区间，在 10 秒细网格上迭代对偶价格 2 万次，上界从 1.005828 降到 **1.004687**（价格证书 `results/dual_prices_second_c10.npz`，`--verify` 约 10 秒重算）。于是"离最优最多差多少"从 1.5% 降到 **0.94%**（0.9952 对 1.0047）。

#### 弹射链用上多核、AI 预测器：做了，但提分很小或没有（如实记录）

- **多线程**（`run_pass_parallel`，默认线程数 = CPU 核数，最多 8；`OBSPLAN_CHAIN_THREADS=1` 恢复单线程）：
  - 做法：每批 8 颗目标，各线程同时找链、解线性规划（只读，不改计划），主线程按顺序检查冲突后提交，冲突的在最新状态上重找。结果与线程调度、核数都无关，可复现。
  - 实测（M1 Pro）：一整遍 30 秒对单线程 33 秒，综合 0.9849 对 0.9847；同样给 30 秒或 1 分钟，综合比单线程高 0.0003～0.0004。
  - 提速不大的原因：同一个站同一夜的时间线大家都在抢，一批里约三成方案互相冲突，只能单线程重找；8 个线程平均只用上约 2 个核。
- **AI 预测器**（`obsplan/chain_ai.py`，模型 `obsplan/models/chain_skip.npz`，默认关闭，`OBSPLAN_CHAIN_AI=1` 打开）：
  - 做法：试一颗目标之前，先用 10 个几微秒就能算出的特征，让小神经网络（与评审网络同一套 numpy 多层感知机）预测"这颗会不会又失败、又白白耗时"，概率高的跳过。特征包括满足 48 小时的候选数、能否直接塞进空当、最大空当、可删的低价值重复观测数、之前失败次数等。
  - 训练数据来自 4 份起点计划上弹射链的 9324 次尝试；默认起点计划（快速档）完全留出，只做测试。
  - 预测本身准确：留出测试的 AUC 是 0.90；阈值 0.8 时能省下约 12% 的试探时间，只丢 1.3% 的成功。
  - **但固定时间内不提分**：给 30 秒时 0.98482 对 0.98469，给 1 分钟时 0.98561 对 0.98597。省下的时间被后面几遍用掉，而那几遍本来也大多失败；同时会误跳过少量本来能成功的目标。所以默认不开。
  - 数据也说明了第二遍弹射链几乎在白忙：默认计划第二遍试了 1081 颗，只成功 57 颗。

### 离最优还有多远：上界（`obsplan/bounds.py`、`scripts/bound_experiment.py`）

上界是一个"天花板"：不管用什么算法，任何合法计划的综合指标都不会超过它。所以"上界 − 我们的计划"就是这份计划离最优**最多**还差多少——真正的最优夹在两者之间，实际差距只会更小。它只需要算一次，不依赖任何一份计划。

两种算法，都是把问题放松（约束变少，合法计划一个不漏），再把放松后的问题精确解出来：

- **网络流上界**：不管任务具体排在哪一刻、是否连续，只要求每个站每 5 分钟的时段里排进去的总时长放得下，就成了一个可以精确求解的网络流问题，约 5 秒。
- **对偶上界**：给每个站的每个 30 秒格定一个价格（就是价格协调算法里的那组价格），每颗目标各自挑"价值 − 价格"最高的观测方案；全部价格之和加上各目标的最优结果就是一个上界。任何一组非负价格都给出合法的上界，价格调得越好上界越低。迭代 6000 次得到的价格存成证书 `results/dual_prices_grid.npz`，`--verify` 用它几秒内重算出同一个数，不需要相信迭代过程。

上界对哪一类计划成立，分三个口径（后一个包含前一个，上界依次变大）：

| 口径 | 对哪些计划成立 | 网络流上界 | 对偶上界 | 采用 |

| 按秒 | 起止是任意时刻的计划（按秒精修后的最终计划）：每个可见窗口两端各放宽一格，并加入格点上不够 120 秒、按秒才够的短窗口 | 1.005828 | 1.005997 | **1.005828** |
| 按秒、不留安全余量 | 同上，并且仰角、太阳高度、地影三项安全余量都取 0 | 1.006676 | 未算 | **1.006676** |

| 计划 | 综合 | 适用的上界 | 离最优最多差 | 换成"不留安全余量"的上界 |
|---|---:|---:|---:|---:|
| H 网格计划（人工放置规则） | 0.9544 | 1.0027 | 4.8% | 5.2% |
| G+ 网格计划 | 0.9615 | 1.0027 | 4.1% | 4.5% |

| G+ + 按秒精修 | 0.9683 | 1.0058 | 3.7% | 3.8% |

- **默认流水线两分钟的结果离最优最多差 3.1%，长跑 7.6 小时的结果最多差 1.5%**。剩下的 1.5% 里有多少是计划还能提高、有多少是上界本身偏松，目前分不开：真正的最优在 0.9904 和 1.0058 之间。
- **第三个口径回答"别的程序不留余量、贴着阈值排，最多能到多少"**：我们的计划为了保证 Skyfield 校验一定通过，在仰角（0.02°）、太阳高度（0.05°）、地影（10 km）上都留了余量。把余量全去掉，上界只从 1.0058 升到 1.0067；长跑结果即使按这个更宽的上界算，离最优也最多差 1.6%。这个口径按本程序的轨道和几何计算，Skyfield 与本程序之间不到 1 秒的差别没有严格计入。
- 按秒口径成立的依据（详见 `obsplan/bounds.py` 开头的说明，`tests/test_bounds.py` 有检验）：按秒合法的任务一定落在某个放宽后的窗口里；得分随时长线性增长、价格在一格内不变，所以"价值 − 价格"的最大值在格点上取到。测试里还用独立写的精确枚举核对了每颗目标的最优结果，并检查了格点计划和按秒精修计划的综合指标都不超过上界。
- 按秒口径下对偶上界从零价格迭代 12000 次到 1.0060，没有比网络流上界更低，所以没有保留它的价格证书。
- 开启月光规避只会让可选的任务变少，上界仍然成立；换规划期、权重或观测时长限制后要重算（`uv run python scripts/bound_experiment.py --flow` 约 1 分钟，首次还要现算一遍不留余量的可见窗口；`--dual grid --iters 6000` 再收紧格点口径）。
- 界面"结果总览"的综合指标下面会显示"离可证明的上界 … 最多差 …%"：网格计划用格点口径的上界，按秒精修过或含按秒任务的计划用按秒口径的上界；场景或规则参数与算上界时不同、或者是演示子集时不显示。

## 泛化检验：换一批场景，伐谋规则还占优吗（稳健模式的由来）

伐谋放置规则是直接在赛题这一份数据上演化出来的。为了看它在没见过的场景上表现如何，用侯治民发布的 synthetic-v0.2 数据集的生成器（同一组种子，提交 f875152）重建了 12 个测试场景的输入：6 个主体场景，加 6 类压力场景各 1 个；目标 1941–12933 颗，站点 5–14 个，规划期分布在 2027 年各月。这些场景没有参与伐谋演化，也没有参与任何调参。每个场景排三遍（高质量模式，含按秒精修）：人工规则（H）、伐谋规则（H+）、稳健模式（两条规则各排一份，取综合高的）。

`uv run python scripts/generalization_experiment.py`（用法见文件开头；结果 `results/generalization.json`；36 份计划的结构检查全部 0 违规）。综合 = 0.5 × 覆盖数/目标数 + 0.5 × 得分/"每颗目标满分观测一次的总分"，按各场景自己的目标数归一；目标少、站点多的场景重复观测多，综合会大于 1。

|---|---:|---:|---:|---:|---:|---|
| 480 主体 | 3727 × 9 | **1.6583** | 1.6442 | −0.0141 | 1.6583 | 人工 |
| 481 主体 | 9864 × 9 | **1.0593** | 1.0533 | −0.0060 | 1.0593 | 人工 |
| 482 主体 | 3346 × 8 | 1.5605 | **1.5624** | +0.0020 | 1.5624 | 伐谋 |
| 483 主体 | 6659 × 10 | 1.3136 | **1.3206** | +0.0070 | 1.3206 | 伐谋 |
| 484 主体 | 8429 × 9 | 1.0892 | **1.0977** | +0.0085 | 1.0977 | 伐谋 |
| 485 主体 | 10081 × 14 | 1.2492 | **1.2767** | +0.0275 | 1.2767 | 伐谋 |
| 570 高负载 | 12933 × 6 | **0.6174** | 0.6132 | −0.0042 | 0.6174 | 人工 |
| 575 低负载 | 1941 × 14 | **1.8504** | 1.8303 | −0.0201 | 1.8504 | 人工 |

- **稳健模式在 12 个场景里都等于两条规则中好的那个**（各选中 6 次），比只用人工规则平均高 0.0043（95% 区间 0.0010–0.0091），比只用伐谋规则平均高 0.0043（0.0012–0.0082），没有一个场景变差。它按精修前的网格综合指标挑选，12 次都与精修后的高低一致。
- **所以产品默认用稳健模式**（`lagrange.solve(portfolio=True)`；命令行默认，`--rule-only` 只用伐谋规则，`--manual-rule` 只用人工规则）。价格迭代两条规则共用，只有放置和局部搜索各做一遍并且并发。机器空闲时实测（10 核 M1 Pro，窗口已缓存）：快速档 40.7 → 41.4 秒，高质量档 62.3 → 68.0 秒，多出的时间在并发的两份局部搜索上。赛题数据上稳健模式选中伐谋规则，计划与 H+ 逐位相同。

## 神经网络放置规则（评审网络）：126 个没见过的场景上的基准

价格协调之后"先放谁"决定了计划的好坏，人工规则和伐谋规则是两条打分公式。这里训练了一个小神经网络（`obsplan/judge.py`，numpy 多层感知机；输入 24 维 = 20 个目标/窗口/价格特征 + 人工、伐谋两条规则的打分），学习"老师"的选择：老师是对每个训练场景单独做的精简长跑（`obsplan/teacher.py`），比稳健模式高 0～0.8%。网络作为第三条放置规则加进稳健模式，和另外两条一起排、取综合高的。

- 场景：synthetic-v0.2 生成器重建的场景，加上新做的 v0.3"像赛题"补充场景（`obsplan/training_data/v3_sampling.py`：高纬度站、更低的低轨、更多中轨；赛题的各项统计落在 v0.3 的 17～83 百分位，v0.2 是 0～100）。训练 120 个（v0.2、v0.3 各 60），验证场景用来调阈值、挑模型，**测试 126 个（v0.2 90 个 + v0.3 36 个）从未参与训练和调参**。
- 流程 `scripts/judge_pipeline.py`（场景 → 老师 → 导出 → 训练 6 个模型 → 调阈值 → 挑模型 → 基准 → 赛题 → 汇总），在阿里云 64 核抢占式实例上跑完。结果 `results/judge_benchmark.json`（逐场景明细）、`results/judge_contest.json`（赛题），模型 `obsplan/models/`（进基准的是 `judge_mix_L`、`judge_v3_M`）。

离按秒上界的差距（%，越小越好；中位数，第一列括号里是平均）：

| 方法 | 全部 126 个 | v0.2 主体 60 | v0.2 压力 30 | v0.3 像赛题 36 |
|---|---:|---:|---:|---:|
| H 人工规则 | 4.28（4.77） | 3.99 | 3.35 | 4.98 |
| H+ 伐谋规则 | 3.65（4.35） | 3.62 | 3.54 | 3.87 |
| **稳健（人工 + 伐谋）** | **3.49（4.09）** | 3.40 | 3.01 | 3.82 |
| 只用网络（judge_mix_L） | 4.46（4.98） | 4.28 | 4.29 | 5.03 |
| 稳健 + 网络（judge_mix_L） | 3.45（4.09） | 3.37 | 3.01 | 3.82 |

- **网络单独用不如伐谋规则**：judge_mix_L 相对 H+ 综合平均 −0.0059（95% 区间 −0.0077～−0.0039），126 个场景 22 胜 104 负；judge_v3_M 平均 −0.0076（13 胜 113 负）。和人工规则大致打平（51 胜 75 负，区间含 0）。
- **加进稳健模式几乎没有作用**：judge_mix_L 平均 +0.00003（区间 −0.00001～+0.00009，4 个场景变好、2 个变差），judge_v3_M 平均 +0.00007（2 个变好）。
- 赛题（8 月 1–7 日，高质量模式）：稳健、稳健 + 网络都是 0.974359（同一份计划，网络这条没被选中），只用网络 0.9604～0.9618；全部 Skyfield 合法。
- **所以默认流水线不加网络**，仍是稳健模式（+ 可选的弹射链）。老师比起点高的部分主要来自多塞重复观测，"放置顺序"本身能学的空间不大（推测，未单独验证）。
- 顺带再次确认了稳健模式：在压力场景里伐谋规则经常输给人工规则（高负载、低负载、高轨为主、区域站网四类都是人工规则更好），稳健模式两边取好的，按中位数在每一组里都不差于两条规则中好的那个。

## 加分项：天气与月光

说明文档："题目没有考虑地球天气和太空天体环境变化，如果可以额外考虑，输出标准结果和考虑之后的结果，可以酌情加分。"

### 标准结果 vs 考虑环境之后的结果（`obsplan/env_report.py`，`python -m obsplan env`）

说明文档要求"输出标准结果和考虑之后的结果"。这里把两份计划放进**同一个环境模型**逐任务检查：

- **月光**：月亮在地平线以上、目标离月亮不到 30° 时天空背景太亮，算观测失败。月亮位置用 DE421 星历，与 Skyfield 校验同源；
- **目标亮度**：按漫反射球估算视星等，暗于望远镜极限星等算看不到。赛题没有目标尺寸，所以统一假设 1000 km、相位角 90° 时为 6 等，极限星等取 15 等；
- **天气**：过去 10 年同期每个站的真实逐小时云量，观测期间每小时云量都 ≤ 30% 才算成功，取 10 年平均。

```
uv run python -m obsplan plan --mode fast --chain 0.5 --out outputs/plan                       # 标准计划
uv run python -m obsplan plan --mode fast --chain 0.5 --moon 30 --validate --out outputs/env   # 考虑月光：规划时就避开月亮 30°
uv run python -m obsplan env outputs/plan/plan.csv outputs/env/plan.csv --out results/env_compare.json
```

| 同一个环境模型下 | 标准计划 | 考虑月光的计划 |
|---|---:|---:|
| 名义综合（不考虑环境） | 0.9844 | 0.9837 |
| 受月光影响的任务 | **1401 个（11%）** | 0 个 |
| 目标太暗的任务（极限星等 15 等） | 7 个 | 9 个 |
| 考虑月光与目标亮度之后的综合 | 0.8884 | **0.9831** |
| 再考虑天气（过去 10 年平均）的综合 | 0.3973 | **0.4425** |

- **规划期正赶上满月前后**（8 月 1 日月面照亮 94%）。标准计划有 11% 的任务撞上月光，考虑之后综合掉了近 0.1。规划时就避开月亮的计划，名义上只少 0.0008，考虑环境之后高出 0.095；再放进真实天气，也高 11%（0.4425 对 0.3973）。两份计划都过了 Skyfield 逐秒校验，考虑月光的那份连月距也一并校验了。
- 目标亮度的影响很小：极限星等取 13、14、15、16 等时，标准计划里太暗的任务分别有 784、113、7、1 个。这和答疑 #43 的"卫星受光照影响可以简化，对结果影响很小"一致。这一项依赖目标尺寸的假设，报告里把几个极限星等的结果都列出来了。
- 网页"天气与月光"页最上方直接展示这张对比表，也可以对当前计划一键做同样的分析。月亮位置每 30 秒精确算一次、中间插值，误差约 0.00001°；这样多进程计算月光窗口时，不会再把内存占满。

- **月光规避**（`config.moon_sep_deg`，默认 0 即不考虑）：月亮在地平线以上时，目标与月亮角距须 ≥ 设定值；月亮位置用 DE421 星历算到地固系，低轨快速移动时在禁区边缘做 1 秒加密；校验器用 Skyfield 独立复核。规划期紧接 7 月 29 日满月，月面照亮比例从 94%（8/1）降到 40%（8/7）；"月亮在地平线以上"的判定也留了 0.5° 余量（按秒精修曾把一个任务推到月出前最后一秒，Skyfield 判为违规，已修复）。
- **天气**（`obsplan/environment.py`）：从 Open-Meteo 历史再分析取各站 2016–2025 年同期逐小时总云量（只发送四舍五入到 0.5° 的站点坐标，结果缓存），云量 ≤ 30% 视为可观测；计划按年回放评估，`lagrange.solve(cell_weight=…)` 按晴空概率做期望价值规划。

| 考虑天气与月光 | 9709 / 27470 | 4436 / 12130 | 0.4236 |

- 真实天气下计划只有约一半能实际完成（期望覆盖 4705 / 9987）。8 月上旬各站晴空概率差别很大：1 号、3 号站约 80%，7 号站（新几内亚）约 1%、8 号站（火地岛）约 6%。
- **8 月口径下按站点晴空概率规划，样本外反而 −2.2%**（10 月口径下 +0.5%）。晴空概率最低的 7、8 号站恰好在南半球冬季、黑夜最长；按概率加权后这些时段几乎被空着，名义覆盖少了 266 颗，而在阴天站点上排观测本来几乎没有代价（失败了也不占别的资源）。只靠气候统计做期望价值规划不可取；要绕开云，需要按实际执行结果动态重规划（见下）。
- 月光规避 30° 的代价很小：名义得分 −0.2%，期望综合 −0.2%。

### 动态重规划：状态更新 → 每天重排（`obsplan/dynamic.py`）

模拟真实运行：每天 0 点（UTC）重新规划剩余时段，只执行当天的任务。当天任务按 ERA5 实况云量判定成败（观测期间每个小时云量都 ≤ 30% 才算成功）；成功的目标不再给覆盖奖励、剩余可观测次数减少、下一次须在这次结束 48 小时后；失败的目标第二天可以再排；过去的站点时段封锁。检验年份是 2024、2025（Open-Meteo 有存档的"提前 1 天 / 2 天发布"预报的两年），气候统计用 2016–2022 年；预报换算成晴空概率时用另一年的预报与实况校准，避免自我验证。

`uv run python scripts/dynamic_experiment.py`（全量 10000 目标，规划期同期 8 月 1–7 日的真实天气，每种策略约 25–200 秒）：

| 策略 | 2024 成功覆盖 / 得分 | 2024 综合 | 2025 成功覆盖 / 得分 | 2025 综合 |
|---|---:|---:|---:|---:|
| 静态标准计划（不看天气，一次排完） | 4635 / 11237 | 0.4187 | 4382 / 10862 | 0.3998 |
| 静态 + 气候统计 | 4336 / 11756 | 0.4123 | 4369 / 10569 | 0.3942 |
| 每天重排 + 气候统计 | 4824 / 12104 | 0.4425 | 4708 / 11247 | 0.4225 |
| **每天重排 + 真实预报** | 4985 / 12224 | **0.4526** | 4770 / 11541 | **0.4305** |
| 参照：每天重排 + 完美预报（当天天气已知） | 5174 / 12702 | 0.4700 | 4943 / 12066 | 0.4478 |
| 参照：事后最优（6 天天气全知） | 5408 / 12841 | 0.4840 | 5188 / 12253 | 0.4632 |

- **闭环重排是基础**：只用气候统计每天重排，就比静态计划综合 +5.7%（两年都是）。原因是静态计划里一次观测赶上阴天，这颗目标就丢了；每天重排时它第二天还能补排。
- **8 月用真实预报还能再 +1.9%–2.3%**：每天重排 + 真实预报比静态计划综合 +8.1%（2024）/ +7.7%（2025），成功覆盖 +7.6% / +8.9%，把"不看天气"与"天气全知"之间的差距补上了约一半（52% / 48%）；完美预报还能再高约 4%。
- 这与原 10 月口径的结论不同：10 月同样两年里真实预报没有额外收益（每天重排本身 +7.8% / +9.9%）。两个季节的预报可用程度不一样，而且检验只有两年，结论要谨慎；方法上都是同一套流程，接上更准的预报源可以直接再评估。
- 不准的预报不能用来"避开阴天"：10 月口径下试过把低晴空概率的时段从窗口裁掉（阈值 0.15、0.3）或"高概率时段排核心计划 + 其余时段贪心补满"，都明显变差。阴天的站点时间本来就闲着，在那里排一次观测几乎没有代价。
- 实现中发现的问题：局部搜索不看晴空概率，只要目标排了任务就算"已覆盖"，哪怕排在阴天。所以"已知的天气"（完美预报、事后最优）用"把窗口裁剪到晴空时段"来表达（`dynamic.clip_windows`），不用权重。

### 突发事件重规划：冻结已执行任务 → 价格协调重排 → 扰动统计（`obsplan/replan.py`）

正式赛题没有突发情况（答疑 #32）；企业赛题初稿要求"持续监测、闭环决策、动态重规划、尽量降低对既有计划的扰动"，这里作为产品演示与加分项（界面"突发重规划"页签）。在事件时刻 t 发生三类事件之一：

- **站点停机若干小时**：t 时正在该站执行的任务中断，停机时段内该站的任务取消；
- **目标升为高优先级**：此后按新优先级计分；
- **新增一个必须观测的目标**（从已有目标里选）：t 之后至少安排一次（与 t 前的观测间隔 48 小时）。

做法：t 之前开始的任务冻结不动；剩余问题用 `dynamic.residual_problem` 生成（各站从 t 起、已观测过的目标从上次结束 48 小时后起），停机时段从窗口里裁掉（`dynamic.clip_cells`）；然后用价格协调 `lagrange.solve` 重排 t 之后的时段（`init_state` 预置冻结状态，`max_obs_left`、`vc_target` 表示已观测次数与已覆盖目标，必须观测的目标给很大的首次奖励），最后按秒精修。两种方式：

- **扰动最小**（默认）：原计划 t 之后仍然可行的任务先放回网格（起止取最近的网格点，与邻居冲突时把网格占位缩短一两格；仍对不上的约 12% 作为固定任务原样保留），价格协调只往空档里补任务，再只为受影响的目标做局部修补（挤让、缩短、挪走或删掉少量低价值任务）。按秒精修时冻结和原样保留的任务固定不动，只有挨着新任务的才跟着微调；
- **全面重排**：t 之后从头规划。

对比口径：同一站、开始和结束都相差不超过 1 分钟算"保留"，同一目标的其余任务配成"移动"（换站、换时间或改时长），原计划剩下的为"删除"，新计划剩下的为"新增"。为此局部搜索与覆盖修复支持了"封锁的时段"和"固定的观测记录"（原有用法的结果逐位不变，已对比验证）。

`uv run python scripts/replan_experiment.py`（结果 `results/replan.json`；在默认流水线 H+ 的计划上，事件时刻 08-03 12:00 UTC，目标取界面推荐列表的第 1 个）：

| 事件 | 方式 | 覆盖 | 综合 | 原任务保留 | 移动 / 删除 / 新增 | 用时 |
|---|---|---:|---:|---:|---:|---:|
| 6 号站停机 6 小时（只取消受影响任务：9904 / 0.9649） | **扰动最小** | **9979** | **0.9677** | 97.0%（6878 个完全不变） | 126 / 101 / 0 | 6 秒 |
| | 全面重排 | 9975 | 0.9624 | 5.5% | 6431 / 605 / 482 | 10 秒 |
| 目标 68131 由中升为高（原计划 t 后观测 1 次） | **扰动最小** | 9994 | 0.9744 | 100.0% | 1 / 0 / 1 | 6 秒 |
| | 全面重排 | 9982 | 0.9692 | 5.2% | 6515 / 542 / 518 | 10 秒 |
| 必须观测目标 63754（原计划没覆盖） | **扰动最小** | 9995 | 0.9744 | 100.0% | 1 / 1 / 1 | 6 秒 |
| | 全面重排 | 9990 | 0.9690 | 5.1% | 6530 / 534 / 537 | 10 秒 |

- 停机 6 小时取消了 6 号站 128 个任务（另有 1 个正在执行的中断）；扰动最小把其中 93 个改到别的站或别的时间，覆盖从 9904 恢复到 9979，只动了原计划 3% 的任务；升级的目标从 1 次观测变为 2 次；必须观测的目标排进了计划，只动了 2 个其他任务。
- 全面重排改动了九成以上的任务，综合指标反而更低：它只能用人工放置规则（伐谋演化的规则不支持按目标设覆盖奖励），迭代也较少，比不上原计划里已经优化好的部分。所以默认用扰动最小。
- 六次重排都通过结构检查（`checks.structural_violations` 的按秒口径），冻结部分逐一相同，停机时段内该站没有任务；界面里可一键做 Skyfield 逐秒校验：停机示例中改动过的 469 个任务 3 秒、事件之后的全部 7347 个任务 48 秒，全部合法。

## 算法效率

### 提速（2026-11-10，计划逐位不变）

`uv run python scripts/bench_pipeline.py --mode fast|quality [--profile]` 给出各阶段用时和计划指纹。窗口已缓存；"规划"含价格协调、局部搜索和按秒精修；10 核 M1 Pro。

| 阶段 | 快速：改动前 → 后 | 高质量：改动前 → 后 |
|---|---:|---:|
| 价格迭代子问题 | 25.6 → 5.7 秒 | 50.9 → 11.9 秒 |
| 伐谋规则打分 | 3.7 → 0.2 秒 | 3.2 → 0.2 秒 |
| 局部搜索 | 36.5 → 24.5 秒 | 56.6 → 39.6 秒 |
| **规划合计** | **76.5 → 39.3 秒** | **121.9 → 63.0 秒** |

上表是只用伐谋规则（`--rule-only`）的用时。默认的稳健模式两条规则各排一份（局部搜索并发）；机器空闲时复测：只用伐谋规则 快速 40.7 秒、高质量 62.3 秒，稳健模式 41.4 秒、68.0 秒，计划指纹相同。

- **价格子问题按计算量均衡分线程**：每颗目标独立求解，按目标编号并行。高轨目标窗口长，计算量集中在少数编号段（前 10% 的目标占 63%），静态分块下一个线程干大半的活，10 线程只快 1.6 倍。改为按计算量从大到小蛇形轮流分到各线程（`lagrange.balanced_order`），每次迭代 169 → 38 毫秒。
- **伐谋规则向量化**：伐谋生成的原始函数逐行用 Python 打分。`obsplan/evolved/vectorized.py` 用同样的运算顺序整列计算，逐位相同；原始代码不动，每次调用均匀抽查 1000 行与原始实现比对，不一致就退回原始实现。
- **覆盖修复剪枝**：挡路任务的损失都不小于 0，插入收益不会超过"直接插入"。找到收益达到这个上限的位置后，就不再扫描（后面不可能严格更好）；前面挡路任务的损失已足够否决时，不再评估后面的。被跳过的试探只会改变观测记录的排列顺序，而用到观测记录的判定都与顺序无关。

全量计划指纹与改动前相同（快速 `621ac90e…`，高质量 `9e966946…`，均为精修前网格计划）；`tests/test_speedups.py` 核对并行顺序、规则向量化、剪枝前后的状态完全相同。试过但没用：按任务缓存"挪走"的搜索结果（挡路任务多在原窗口附近挪动，命中率低，反而慢 30%）；numba 动态分块（当前线程后端不支持）。

## 局部最优性检验：CP-SAT 分段精确重排（`obsplan/lns.py`）

全量 CP-SAT 解不动，但单站 2 小时的子问题几秒内能求最优。`run_lns` 每次取一个站点的一段时间，拿掉段内任务、其余固定，用 CP-SAT 在段内精确重排，变好才接受。
在方案 H 的计划上随机试 89 段（8 月口径共 320 段，240 秒）：17 段有改进，累计综合指标只提高 0.0005（10 月口径下试 35 段只提高 0.0001）。说明现有计划在 2 小时尺度上已接近局部最优，G+ 的优势来自全局结构而不是局部排布，因此不放进默认流程；它可以作为方案 G 在全量上使用 CP-SAT 的方式（局部子问题求解器，而不是全局求解器）。

## 主要发现

1. **局部搜索比构造方式更关键**：同一套局部搜索（挤让插入、压紧碎片、按单位时间收益分档补空、延长）让 D 从 0.896 到 0.939、G 从 0.814 到 0.962。
2. **规划期决定问题形态**：10 月口径下覆盖是难点（H 最好）；8 月口径下 9999 颗都可见、夜短，覆盖接近饱和，难点变成在有限站点时间里塞进更多重复观测，CP-SAT 分块排得更紧，G+ 略好于 H，但慢 5 倍。
3. **全量 CP-SAT 解不动**：8 小时块约 3 万个可选区间，20 秒内无可行解；只能缩到 4 小时块、每目标每块保留 1 个窗口；每块限时降到 2 秒就找不到可行解。
4. **H 的优点**：用时短；不需要训练权重，覆盖/得分权重变化时直接适用；对偶值给出上界；时间格价格可直接解释"为什么排在这里"。
5. **按秒精修对所有方案都有效**：网格窗口两端的零头秒数加起来，在 8 月口径下让 H 的得分 +2.6%，只多 4 秒。
6. **不同方案的计划可以互补**：三份计划几乎没有完全相同的任务，合并成候选池再用 CP-SAT 求解，比任何单个方案都好（0.978）。CP-SAT 在全量上直接求解不动，但在"几份好计划及其变体"组成的池上，按 24 小时分块每块不到 1 秒就能解到最优。

7. **伐谋找到的规则比人工规则和我们手写的改进都好，但评测场景决定成败**：同一个演化对象做了三次，用子场景评测的两次，规则只在子场景上变好；直接用全量实例评测的第三次，第 1 名在全量上 +0.82%（我们手写的"推荐窗口加分"规则为 +0.39%）。赛题只有一个实例，演化评测就该直接用它。反过来，换到 12 个没见过的合成场景，这条规则与人工规则 6 胜 6 负；产品默认两条都排、取好的（见"泛化检验"）。

## 实现中处理过的坑

- 优先级清单编号去掉了前导零、Alpha-5 编号已转数字，需规范化后匹配（否则丢 783 颗）。
- 外推到原 10 月口径（离 TLE 历元约 2 个月，已作废）时，部分 TLE 的 SGP4 不报错却给出上千万公里外的位置；30 秒采样会把它"混叠"成正常过境。按 TLE 自身近地点/远地点做合理性检查后剔除。
- 近天顶过境每秒移动约 1°，85° 上限必须在每次过境峰值附近做 1 秒加密检查。
