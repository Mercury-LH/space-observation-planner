# 六档规划：选择计算投入，保留共同规则

六档将已实现的 H+ 与 H+/G+/E 融合流程接到同一个滑条上。滑条是离散方案选择器：向右选择更多价格迭代、更完整的局部搜索，最后加入多来源融合。它不会对已有计划插值，也不保证每次运行的质量和实际耗时都严格递增。

## 启动与操作

在仓库的 `方案H初版/` 目录执行：

```bash
uv sync --frozen --extra app
uv run streamlit run app/streamlit_app.py
```

浏览器打开 `http://localhost:8501`，在左侧“新建规划”中选择“六档自动规划”，拖动“计算档位”，然后点击“运行规划”。**拖动只选择配置，不运行求解器**。`instant` 表示最快档；全量计划仍需要求解、按秒精修和独立校验，第一次运行还需要准备数据与可见窗口。

默认实例是 10000 个目标、10 个站，规划期为 **2026-08-01 00:00 至 2026-08-07 00:00 UTC**。界面允许调整规则与演示范围；调整后必须根据新实例的实际输出判断，不能直接套用旧参考值。“自定义算法”入口保留 H/E/B、天气规划与自定义质量权重，作为独立研究对照。

## 六档实际执行什么

唯一档位目录是 [`obsplan/effort.py`](../obsplan/effort.py)，底层参数复用 [`obsplan/portfolio.py`](../obsplan/portfolio.py) 的预设。

| 档位 | portfolio 预设 | H+ 迭代 | H 局部搜索 | 来源与融合 | 证据状态 |
|---|---|---:|---|---|---|
| instant | `hplus_fast` | 1 | 快速 | 仅 H+，不融合 | 同条件确认 |
| medium | `hplus_fast` | 10 | 快速 | 仅 H+，不融合 | 同条件确认 |
| high | `hplus_fast` | 30 | 快速 | 仅 H+，不融合 | 探索，待同条件复核 |
| xhigh | `hplus_fast` | 75 | 快速 | 仅 H+，不融合 | 探索，待同条件复核 |
| max | `hplus_fast`，覆盖 `h_fast=False` | 300 | 完整 | 仅 H+，不融合 | 同条件确认 |
| ultra | `fusion_baseline` | 300 | 完整 | 从头生成 H+/G+/E，三轮融合 | 同条件确认 |

六档都运行已经采纳的本地伐谋排序规则 `obsplan/evolved/recover_rule.py`，然后按秒精修，并由 Skyfield 对最终计划进行独立 **1 秒步长**校验。ultra 的 H+ 来源使用同一规则，E/G+ 来源与融合成本也全部计入求解时间。日常规划不实时请求云端伐谋 agent，不需要 API key；云端规则演化是另一条工作流，见 [自动评测与协作](自动评测与协作.md#伐谋在哪里)。

增加计算档位不会放宽仰角、夜间、目标受照、最短观测、切换或跨站重复间隔等硬约束，也不会改变内部质量定义。自动六档固定覆盖和观测分各 50%、`sumP` 归一化。1 秒采样是独立数值复核，不是解析连续时间证明。结果会连同校验状态保存；未通过或未完成校验的结果不能进入推荐排名。

如果独立校验未完成，可在“校验与导出”点击“重试独立校验（保留原计划）”，无需再次运行求解器。重试耗时记录在 `notes["revalidation_time_s"]`，不覆盖首次运行的计时；摘要 JSON 中缺失或非有限几何余量导出为 `null`。

## 已确认前沿与探索点

当前确认的是**同一条件下已测候选集合中的四个非支配点**：没有其中另一个点同时取得不低的质量与不长的求解时间，并至少一项更好。它不证明所有可能配置的全局前沿，也不证明六个滑条档位都是 Pareto 最优。

| 档位 | 历史覆盖 | 内部质量 Q | 历史求解秒 | 历史端到端秒 | 证据 |
|---|---:|---:|---:|---:|---|
| instant | 9911 | 0.961049 | 72.46 | 179.37 | 同条件确认 |
| medium | 9933 | 0.963861 | 79.24 | 186.04 | 同条件确认 |
| high | 9958 | 0.965490 | — | — | 探索结果 |
| xhigh | 9984 | 0.969326 | — | — | 探索结果 |
| max | 9994 | 0.974359 | 176.97 | 284.69 | 同条件确认 |
| ultra | 9998 | 0.978157 | 1515.10 | 1626.72 | 同条件确认 |

四个确认点来自 2026-10-24 的 **Apple M5、8 线程、接通电源且低电量模式开启、热几何缓存、固定 8 月 1–7 日全量实例**。数据来源为已发布的 [`summary.json`](../results/time-aware-2026-10-24/summary.json)，完整条件、复跑数及各组结果见 [实测报告](../results/time-aware-2026-10-24/README.md)。表中使用报告聚合值，不是当前设备预测；更换设备、供电、缓存、代码、日期、规则、目标或站点后，等待时间和质量都可能变化。

high/xhigh 的计划已经过独立校验，质量可作为探索参考，但探索时没有逐次记录可核实的功耗条件，尚不能与四个确认点构成同条件时间比较。因此界面保留它们的质量与覆盖、留空时间，并且不把它们画入确认前沿。不从相邻两档插值或推算耗时。

这里的 Q 是团队内部质量指标，计算方式见 [自动评测与协作](自动评测与协作.md#两种得分分别表达什么)，不是官方比赛成绩。滑条表示计算投入选择，不自动替用户重新定义质量/时间权重。多线程 CP-SAT、限时搜索和实例变化都可能改变结果顺序；更高档位不承诺每次质量更高，更多搜索预算也不等于固定等待时长。

## 队友与 AI 的统一接口

`get_effort(name)` 返回冻结的 `EffortProfile`，包含档位名称、说明、实际预设、证据状态与可空的历史参考值。`EFFORT_ORDER` 定义固定显示顺序；未知档位抛出 `ValueError`，不静默回退。UI 不应另写一份参数表。

只需要标准求解参数时：

```python
from obsplan.effort import get_effort, spec_for_effort

profile = get_effort("medium")
spec = spec_for_effort(
    "medium", seed=2026, workers=8, full_problem=True,
)
# spec 是公共 portfolio 预设的独立深拷贝。
# 可交给 portfolio.solve，或作为统一 benchmark 的 solver spec。
```

界面或其他本地产品应调用包含最终独立校验的入口：

```python
from obsplan.app_backend import run_effort

# pb 是已经建立的公共 Problem。
# on_progress 可省略；签名是 on_progress(fraction, message)。
run = run_effort(
    pb, "medium", progress=on_progress,
    full_problem=True, workers=8,
)
assert run.notes["effort_level"] == "medium"
legal = run.validation["legal"]
```

实际签名为 `run_effort(pb, effort, progress=None, full_problem=True, workers=8) -> Run`，随机种子取 `pb.cfg.seed`。它通过 `spec_for_effort` 调用公共 `portfolio.solve`，保留实际参数、阶段耗时、伐谋执行说明及校验结果。`portfolio.solve` 本身只是求解器；直接调用它不会代替最终独立校验，正式评测应由 benchmark 接手。

对子集必须传 `full_problem=False`。这会设置 `finish_near=False`，关闭可能补入全量目标的 near-window 补充步骤；常规精修和独立校验仍执行。不能因为子集更小就省略约束、改变归一化含义，或把子集输出标成全量结果。

进度条表示阶段推进，不是剩余时间预测。新运行保存自己的实际指标，历史参考表保持固定：

| 字段 | 计时范围 |
|---|---|
| `run.runtime_s`、`notes["solver_time_s"]` | 完整 `portfolio.solve` 调用，含来源生成、搜索、融合和精修 |
| `notes["preprocessing_time_s"]` | `run_effort` 内公共 near-window 准备 |
| `notes["validation_time_s"]` | 最终独立 1 秒步长校验 |
| `notes["total_time_s"]` | `run_effort` 内准备、求解与校验；不含上游建立 `Problem` |
| `notes["ui_total_time_s"]` | 界面从点击运行后的数据/窗口/子集准备至校验结束；不含保存和页面绘制 |

历史表的“端到端”来自 benchmark 的独立进程计时，不能直接解释成某次界面的 `total_time_s`。新的性能结论请继续用 [`obsplan.benchmark`](../obsplan/benchmark.py) 串行复跑，固定环境与缓存口径，保留全部记录。修改档位、求解器或规则后，更新相应配置和测试，并重新提供证据；不得覆盖历史实验来让新滑条看起来单调。
