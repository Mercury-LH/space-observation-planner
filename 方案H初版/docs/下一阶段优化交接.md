## 当前已经完成的基线

标准实例为 **10000 目标、10 站、2026-08-01 00:00 至 2026-08-07 00:00 UTC**。构造候选使用 30 秒时间网格，最终计划按整数秒精修。所有推荐必须通过独立 Skyfield **1 秒步长**数值校验，保留任务端点检查与全部硬约束；这不等于连续时间解析证明。

内部质量为 `Q = 0.5 × covered / N + 0.5 × observation_score / sumP`，标准实例 `N=10000`、`sumP=30062`。时间加权指标为 `J=100×((1-w)×Q+w×120/(120+T))`，默认 `w=3/7`，`T` 为完整求解时间。权重来自公布的结果/效率 40:30 占比，但运行秒数换分函数由团队定义；**Q、J 以及下文优化阈值均非官方比赛成绩或要求**。重复观测可得分，因此 Q 不保证小于等于 1。

| medium | H+ 10 轮，快速局部搜索与精修 | 9933 | 0.963861 | 79.24 | 同条件确认 |

四个确认点在这一同条件候选集合中均非支配。high/xhigh 的计划已经过独立校验，但探索时没有逐次记录可核实功耗条件，所以不填可比时间，也不加入四点确认前沿。六档是计算投入选择，不保证每次质量、实际耗时或覆盖严格单调；不能称为六个全局 Pareto 最优点。`instant` 是最快档，仍需要计算与校验；界面拖动只选择配置，点击按钮才求解。

H1 需要准确解释：`h_iters=1` 从零价格开始，最终使用的 `best_mu` 仍是零；它是**零初始价格下的伐谋规则恢复与精修基线**，不是充分收敛的价格协调结果。下一阶段不能只增加迭代次数就宣称方法更优。

- **探索组**：`full-v1`、`iteration-v2`、`repeat-v3` 缺少逐次功耗记录，仅保留探索证据，不事后补造模式或混排时间。

## 下一阶段优先级与可量化验收

以下是建议的团队目标，可在执行前依据资源调整并记录，不能在看到结果后更换标准以挑选有利运行。

**第一优先：补齐 high/xhigh 同条件校准。** 选择当前可稳定保持的一个供电环境，冻结代码、数据、配置、依赖、8 线程与缓存口径。建议六档各跑 3 次，预先固定种子 2026/2027/2028，并在同一实验设计内复跑所有对照；若资源仅允许先跑五个 H 档位，应明确“仅 H 家族校准”，ultra 暂时保留历史证据。不要拿新 high/xhigh 秒数与旧 AC1 秒数直接合并。

校准成功标准是计划全部完成独立校验、环境快照可比、全部运行含失败均保留，并给出覆盖/观测分/Q/求解与校验及端到端时间的中位数和范围，重新计算实际非支配集合。high/xhigh 被其他档位支配也是有效结论，可以据此调整推荐，不要求人为保持六个前沿点。校验失败、供电变化、混用源码或不明缓存条件则不能形成确认结论，不能用插值填缺失秒数。

**第二优先：profiling H 恢复与局部搜索。** 先复用现有阶段计时，再定位 `lagrange.solve` 中恢复、特征构造和局部搜索的占比。测量工具会改变耗时，profiling 运行只定位热点，正式候选需关闭 profiling 后从头计时。优先消除重复计算、减少候选遍历与数据转换；暂不改公共规则、独立校验器或 Q 定义。

建议采纳门槛：同条件、相同种子计划全部合法；对预先选定 H 基线，至少满足以下一项，并且没有新增非法、异常或超时：

1. 每个配对种子 Q 不下降（浮点比较容差建议 `1e-9`）、覆盖不减少，求解时间中位数至少降低 **10%**；
2. 每个配对种子 Q 不下降、覆盖不减少，Q 中位数绝对提高至少 **0.0005**，且求解时间中位数不增加。

若收益落在基线运行波动内，记为“未确认”；先追加同设计复跑，而不是宣布加速。若质量与速度互有损益，则完整报告新的 Pareto 点与固定权重 J，只作为偏好不同的候选，不称为严格支配原基线。阶段提速被其他阶段抵消、总体中位数未达到门槛、或任何结果违规均不满足该优化目标。小于门槛但确有收益的变更可单独作为工程改进审阅，不冒充主要性能进展。

**第三优先：降低 G 与融合成本。** AC1 融合基准中，G 构造约 **487.23 秒**、G 局部搜索约 **31.00 秒**，三轮融合求解合计约 **598.98 秒**、融合后局部搜索约 **133.11 秒**；见 [同次运行的阶段摘要](../results/time-aware-2026-10-24/confirmation/confirmation-v4/001-fusion_baseline-r1/result.json)。先验证当前瓶颈是否仍相同，再一次改变一个因素，例如 G 每块时限、候选筛选、融合轮次或早停。每次仍从头生成来源计划，完整记录 GA、E/G/H、建池、建模、局部搜索与精修成本。

建议以新环境中重新测得的 `fusion_baseline` 为对照：全部合法、每个配对种子 Q 不下降且覆盖不减少，完整求解时间中位数降低至少 **20%**，才作为“融合质量保持的加速”目标达成。若不能保持质量，可以保留为较低预算候选，但必须在同条件下重新计算 Pareto 集合与 J；被现有 H 档位同时以更高质量和更短时间支配，则停止该候选方向。不能只把融合最后一步缩短、漏记来源生成时间来达成目标。

## 共享代码包与接口

六个目录位于 [`计算档位/`](../计算档位/) 下：`instant/`、`medium/`、`high/`、`xhigh/`、`max/`、`ultra/`。每档提供 `run.py` 和 `README.md`，共用 `计算档位/runner.py` 与 `obsplan/` 底层；**不要复制六套核心算法再分别修改**。suite 从当前档位目录动态解析，不维护六份容易漂移的静态 `suite.json`。

在 `方案H初版/` 执行下面的第一条命令只查看完整配置，不启动求解；第二条命令会实际运行两次统一 benchmark，属于后续正式实验，安排好环境与时间后再执行：

```bash
uv run python 计算档位/high/run.py --show-config
uv run python 计算档位/high/run.py --output outputs/effort/high-run1 --repeats 2
```

评测入口返回后保存 `source-suite.json`，保留本次传入的配置来源；若聚合因环境冲突提前报错，各次运行的 `request.json` 仍保留完整参数。还可设置线程、种子、超时和时间权重，参数细节见各档 `--help` 与目录说明。每次使用新输出目录。进入自动生成的 suite 后仍执行相同的独立校验、指纹和功耗检查，文件夹入口不绕过公共评测器。

| 层次 | 稳定接口或入口 | 用途 |
|---|---|---|
| 档位目录 | `obsplan.effort.get_effort(name)` | 返回不可变元数据与历史证据，未知档位报错 |
| 标准配置 | `spec_for_effort(name, *, seed=2026, workers=8, full_problem=True)` | 深拷贝公共预设，供产品与评测共同使用 |
| 统一求解 | `obsplan.portfolio.solve(pb, spec, progress=None) -> (Schedule, info)` | 从头求解；新算法可注册同签名插件 |
| 产品执行 | `obsplan.app_backend.run_effort(pb, effort, progress=None, full_problem=True, workers=8) -> Run` | 种子取 `pb.cfg.seed`，自动最终独立校验与状态保存 |
| 正式性能实验 | `python -m obsplan.benchmark run/report` | 固定配置、隔离进程、计时、指纹、功耗检查与报告 |

`Schedule` 的站点/目标是公共数据集零基索引，开始和持续时间必须是有限整数秒。演示子集必须传 `full_problem=False`，关闭可能从全量补入目标的 `finish_near`；不放宽其他约束。`portfolio.solve` 本身不替代最终独立校验。界面的 `ui_total_time_s` 包含上游数据/窗口准备，后端 `total_time_s` 从 `run_effort` 开始计时；与 benchmark 历史端到端范围有区别，详见 [六档规划](六档规划.md)。

伐谋实际调用链为 `portfolio.solve → lagrange.solve(rule=load_rule()) → recover_rule.score`。当前六档执行已演化、审阅并采纳的本地 Python 规则，运行时云端调用数为 **0**，不需要 API key。规则来源见 [`recover_rule.py`](../obsplan/evolved/recover_rule.py) 文件头与 [`integrations/famou_h/`](../integrations/famou_h/)。后续云端演化需单独安排实验、候选复评和采纳检查；不要为日常 benchmark 自动开云实验，不硬编码或提交任何凭据。
