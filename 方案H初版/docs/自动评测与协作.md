# 自动评测与队友协作

本装置把求解、独立校验、计分和报告统一起来。团队迭代时只替换求解器，同一份计划必须经过相同的规则和校验。默认使用完整 10000 目标 × 10 站 × 6 天实例，规划期为 2026-08-01 至 08-07 UTC。

这里的 E、G+、H+ 都调用 H 目录内已有的共同规则实现，复现当前最强融合流程；不是直接执行旧 `方案E初版/` 或 `方案G初版/` 中尚未统一日期和几何的程序。旧目录算法迁移时应通过下方插件接口适配公共 `Problem` 和 `Schedule`，再从头评测。

`benchmarks/baselines.py` 提供人工多因素贪心与固定优先级贪心两个低成本对照，用于检查更复杂方法是否值得运行。它们不使用伐谋，不能仅凭内部效用高就视为满足赛题“必须使用伐谋”的正式提交方案；推荐时同时检查这一交付要求。排行榜的“合法”特指观测计划通过独立约束校验。

## 两种得分，分别表达什么

质量指标沿用现有 H 分支的比较口径：

```
Q = 0.5 × covered / N + 0.5 × observation_score / sumP
```

`covered` 是被合法观测的不同目标数；`observation_score` 包含满足间隔条件的重复观测；本实例 `N=10000`、`sumP=30062`。观测 120 秒取得基础分的 60%，120–240 秒线性增加，达到 240 秒为满分。240 秒是计分饱和点，不额外解释成禁止更长任务的官方硬约束。

《开运联合/说明.docx》的“评分细则”写明：**计算结果40%、产品体验30%、算法效率30%，额外加分最多10%**；仓库根目录 `规则口径.md` 第18项采用相同口径。计算结果内部的覆盖/累计观测分各占一半。当前文档没有公布运行时间换算为效率分的公式，也没有给出固定求解时限。

本轮保持产品界面相同，只比较算法，按质量∶效率=40∶30归一化，因此默认 `w=3/7≈0.428571`。时间效用仍是团队的代理函数，不等于主办方效率分：

```
speed(T) = 120 / (120 + T)
J(w) = 100 × ((1-w) × Q + w × speed(T))
```

`T` 是完整求解耗时，包含 H 迭代、GA 训练、E/G 计划生成、建池、建模、融合、局部搜索和按秒精修；不能只计最后一次合并。`w=3/7` 是依据已公布分项占比的默认选型权重，并同时报告 `0、0.1、0.2、0.4` 的敏感性结果。120 秒是事先固定的速度尺度，换候选集合不会改变同一运行的分数。更快总是得到更高速度效用，但收益逐渐饱和。

这两者都是**内部指标，不是比赛官方评分**。由于 `sumP` 只对应每个目标满分观测一次，而题目允许重复，`Q` 理论上可能大于 1，`J` 也不承诺以 100 为上限。比较时必须同时展示覆盖、原始观测分和耗时。

窗口/数据预处理、求解、独立校验和进程端到端耗时分别记录。默认 J 只对求解耗时加权，适合团队多次迭代同一实例；完整交付等待时间应看端到端。1 秒步长 Skyfield 校验是独立数值复核，不是连续时间的解析证明。未校验、非法、异常或超时的运行保留记录，但不能获胜。

耗时比较还必须固定供电与低电量模式。macOS 的 `power_profile` 记录当前供电源（`AC` 或 `Battery`）以及该供电源对应的 `lowpowermode` 设置，并参与环境指纹；电量百分比和充电剩余时间不进入指纹。程序在预处理开始、完整求解结束、校验结束三个边界保存快照。任一快照与开始不同，运行标记为 `environment_changed`，保留计划、质量指标和校验结果，但不进入排名；之后切回初始设置也不会撤销已观察到的变化。

非 macOS、命令不可用、读取超时或无法解析时，相关状态记为 `unknown`，不能解释为低电量模式已关闭。边界采样不能发现两次采样之间切换后又切回的情况，也不测量热降频或其他进程的资源竞争。即使所有快照相同，仍应固定系统设置、保持串行运行并复跑推荐候选；含 `unknown` 的结果不能单凭这个字段证明功耗条件相同。自动评测只读取系统状态，不会替用户修改供电或低电量设置。

## 运行和接口

以下命令均在仓库的 **`方案H初版/` 目录**执行，使用 Python 3.12 和锁定依赖。从仓库根目录开始：

```bash
cd 方案H初版
uv sync --frozen
uv run python -m obsplan.benchmark run --suite benchmarks/default.json --output outputs/benchmarks/full
```

每次运行使用新的输出目录。完整基准需要生成 G 的全部滚动块并完成融合，耗时明显长于只跑 H+。先做快速开发检查，再进行完整正式对照；不要在正式计时期间同时跑其他算法或测试。

交互式六档规划使用相同的 `portfolio.solve`，启动方式：

```bash
uv sync --frozen --extra app
uv run streamlit run app/streamlit_app.py
```

界面滑条按 `instant / medium / high / xhigh / max / ultra` 依次映射到 H+ 1/10/30/75 轮快速局部搜索、H+ 300 轮完整局部搜索、H+/G+/E 三轮融合。六档均包含本地伐谋规则、按秒精修和独立 1 秒步长校验；拖动不触发求解，只有点击“运行规划”才计算。`instant` 是最快档，仍有计算及校验等待。

统一档位定义在 `obsplan.effort`：`get_effort(name)` 返回不可变说明与历史证据，`spec_for_effort(name, *, seed=2026, workers=8, full_problem=True)` 返回独立参数字典。产品入口为 `obsplan.app_backend.run_effort(pb, effort, progress=None, full_problem=True, workers=8) -> Run`，种子取 `pb.cfg.seed`，自动执行公共求解器和独立校验。演示子集必须传 `full_problem=False`，关闭可能补入全量目标的 near-window 步骤，不放宽硬约束。具体示例和计时字段见 [六档规划](六档规划.md)。

界面的固定历史参考只有 instant、medium、max、ultra 四个同条件确认前沿点；high/xhigh 为尚未按同一功耗条件复核的探索点，只显示探索质量，不估计耗时。四点来自 Apple M5、8 线程、AC 低电量模式、热缓存、固定 8 月 1–7 日全量实例。它们不是新设备的性能预测，也不能证明所有可能方案的全局前沿；各档位的实际质量与耗时不保证单调。界面运行适合检查与使用方案，新的正式性能结论仍须按本页的 benchmark 流程记录环境并复跑。

```bash
# 只跑快速方法；推荐方案至少复跑一次
uv run python -m obsplan.benchmark run --presets hplus_fast --repeats 2 --output outputs/benchmarks/fast-repeat
# 同一冻结代码、输入、规则和环境下合并后续试验，并重新选时间权重
uv run python -m obsplan.benchmark report outputs/benchmarks/full --include outputs/benchmarks/fast-repeat --time-weight 0.42857142857142855
```

输出包括总表 `report.md`、`summary.json`、运行清单 `manifest.json`，以及每次运行的 `result.json`、`plan.csv`、`worker.log`。后两项只留本地。公开摘要保留配置、求解器参数与指纹；对照数据/规则/公共代码/环境不一致时拒绝合并。同名方法参数不同也拒绝合并，调参时请使用不同的试验名称。

自定义配置示例（保存为另一个 suite JSON，`solvers` 中的名称用于报告）：

`utility`、`aggregate` 和未指定权重的 suite 统一使用 `DEFAULT_TIME_WEIGHT=3/7`。自定义 suite 仍建议显式写出 `time_weight` 和 `time_scale_s`，便于审阅和复现；已有实验显式指定的权重不变，报告默认使用其 manifest 中保存的值。

```json
{
  "presets": ["hplus_75"],
  "workers": 8,
  "repeats": 1,
  "time_weight": 0.42857142857142855,
  "time_scale_s": 120,
  "solvers": {
    "hplus_75": {
      "entrypoint": "obsplan.portfolio:solve",
      "spec": {"preset": "hplus_fast", "h_iters": 75}
    }
  }
}
```

GitHub Actions 的 `Planner evaluation contract` 在相关提交/PR上运行合成接口测试；手动 `workflow_dispatch` 可以选 `hplus_fast` 或 `all` 跑全量实例，只上传摘要。CI采用2线程，其速度结果不能与本地8线程混排。完整新工作流在默认分支合入前可能尚未出现在 Actions 的手动入口，可先使用上述本地命令。

`benchmarks/confirmation-v4.json` 用于最终同模式确认：一次运行 `fusion_baseline`、`hplus_1_fast`、`hplus_10_fast` 和 `hplus_300_full`，固定 8 线程、每个进程最多 3600 秒、时间权重 `3/7`。这组实验用于确认探索阶段筛出的候选，随后还应复跑赢家；不同供电模式的探索结果保留为历史证据，不合并计算速度排名。

统一求解函数：

```python
def solve(pb, spec, progress=None):
    # pb: 公共 Problem，包含 Config、Dataset、Windows 和价值系数
    # spec: 预设及覆盖参数；progress 可接收阶段事件字典
    # Schedule 中 station/target 为 pb.ds 的零基索引
    # start_s 相对规划起点；dur_s 为持续秒数；均要求整数秒
    return schedule, {
        "stage_timings_s": {},  # 阶段名 -> 实测秒数
        "actual_config": spec, # 填入包括默认值在内的实际参数
        "famou": {"mode": "unused", "runtime_cloud_calls": 0},
    }
```

注册预设位于 `obsplan/portfolio.py`。要比较独立算法可使用受信任的 `module:function` 插件，仍必须返回 `Schedule`。插件会在本地执行，独立进程用于限制耗时和隔离运行状态，并不等于不可信代码沙箱。

插件模块的顶层只能定义函数、常量和导入依赖；禁止在导入时求解、读取已生成计划或访问云端。所有候选生成、训练和搜索必须放在 `solve` 中，才能完整计入求解时间。新进程的依赖导入记在预处理；Numba磁盘编译缓存状态另行记录，未命中的编译成本计入实际求解，不扣除估算值。窗口和 near-window 公共几何在求解计时前统一准备。

外部插件的自动源码指纹覆盖入口文件，加上公共 `obsplan/` 与 `integrations/` 源码；不递归追踪任意第三方辅助模块或模型文件。最简单的协作方式是把新算法放在一个有版本名的入口文件中，复用公共库；若还有外部资产，应另行固定版本、保存哈希并附到实验记录中。公共代码改动后重新跑基准，参数调节或新增独立插件可在公共指纹一致时合并对照。

标准适配器当前要求 30 秒构建网格、质量内部权重各 0.5、`sumP` 归一化。更改这些语义需要同步修改融合目标系数并补对照，不能只改配置后继续沿用旧结论。数据和完整配置参与缓存指纹，避免拿旧窗口评价新规则。

## 为什么 G 会显著变慢

默认 G 每次看 4 小时、提交 3 小时的计划。6 天对应约 48 个滚动块，每块 CP-SAT 搜索上限 10 秒，仅搜索预算就可能接近 480 秒，还要加 GA、候选筛选、建模和局部搜索。之后三源融合还要扩大候选池、建模和重解。H+ 主要用价格迭代和贪心恢复，成本结构不同。

因此，融合的质量收益要与全部新增耗时一起计算。新的阶段日志会区分 `g_construct`、`g_local_search`、`ga_train`、建池、融合和精修；缩短 G 预算、减少融合轮数、或移除 G 都是要实测的选项，不能只凭旧结果断言一定更好。

## 伐谋在哪里

日常调用链是 `portfolio.solve → lagrange.solve(rule=load_rule()) → recover_rule.score`。这是执行已经采纳的 Python 排序规则，不会访问伐谋 API。H+ 仍使用本地引擎检查候选可行性，并由独立校验器复核最终计划。

赛题汇编“伐谋与参赛AI程序的关系”一节允许伐谋参与算法生成、优化、演化或策略探索，并未要求每次规划实时调用云端。这里采用“云端演化、运行时本地执行”的架构；提交材料应保留实验编号、规则源码和端到端复评证据，不能把这一过程描述成每次规划都有在线 agent。

云端 agent 出现在另一个环节：通过 `scripts/famou_ctl.py` 创建实验 → 伐谋生成候选规则 → 本地 evaluator 评测 → 回传指标 → 下载并复评候选 → 审阅、采纳到 `obsplan/evolved/`。历史实验说明见 `integrations/famou_h/README.md`。自动评测本身不启动云实验，也不需要 API key。

已采纳规则来自针对本题固定全量实例的演化，属于本实例上的优化结果；对其他规划日期、站点或目标集的泛化需要另外测试。后续演化如果也要优化速度，应把同样的时间指标加入 evaluator，并为评测固定预算和线程，最终仍从头运行完整计划作采纳检查。

## 给队友的迭代流程

1. 先读 `方案H初版/AGENTS.md`、仓库根目录 `规则口径.md`、最新实测报告和对应机器可读摘要。
2. 从自己的分支修改一个明确因素，保留标准基准；新增求解器遵守公共接口。
3. 运行相关合成测试和小规模开发检查，再以相同机器、配置、依赖、线程、缓存口径做完整串行对照。
4. 同时报质量和速度，保留失败/超时；查看不同时间权重和 Pareto 前沿，避免只优化一个显示出来的总分。
5. 推荐候选至少再跑一次，检查波动和 Skyfield 校验，最后提交代码、配置、摘要与复现命令。
6. 不提交凭据、目标明细或大缓存；在 PR 中交代问题、变化、实测收益、代价和适用范围。
