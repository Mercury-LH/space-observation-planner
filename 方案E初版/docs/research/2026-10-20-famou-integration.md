## 本地评测契约

默认真实数据开发场景是 `congested_300_1h_run01`：
300 个目标、2 个站、1 小时。时间缩短和站点选取是用于制造容量竞争的
开发设置，不等同于正式六天实例。

候选只能实现 `solve(instance)`，接收窗口、优先级、规则、时限和固定随机种子，
返回观测记录。每个候选在独立进程内执行；本地再次校验窗口包含、时长、
同站资源冲突、30 秒切换、每目标最多一次以及重算 10–85 度仰角。
候选无权修改评价器来影响分数。

优化顺序仍为覆盖优先、得分次之。返回给伐谋的
`combined_score = (C + S/(P+1))/(N+1)`：

- `C`：覆盖目标数；
- `S`：优先级与观测时长得分；
- `P`：全部目标优先级权重之和；
- `N`：目标数。

由于次项严格小于 1，多覆盖一个目标始终优于任意次项分数变化。
这一数值只用于演化排序，不是比赛百分制总分。

默认每例候选执行上限 20 秒，只用标准库，固定种子与修复迭代数。
macOS `sandbox-exec` 阻止读取仓库、密钥和原始资料，阻止联网及子进程，
仅允许写指定输出文件。输出文件、CPU 时间与总运行时间有限制。
目前没有 RAM 硬上限，因此采用单并发；不宣称完全的资源隔离。

专用 worker 拒绝云端提供的额外依赖，避免原生 SDK 在评测器外自动安装
依赖。它检查实际云端状态并在停止时排空任务、上报结果。
SDK 本地测试可能将 `validity=0` 仍称为 “Test passed”，包装器会在 JSON
输出中单独检查合法性，并用非零退出码报告失败。

它与第一阶段算法预算不同，不能据此宣称同预算性能提升。

SDK 本地测试已实际返回 `validity=1`、`geometry_checked=1`。

这证明链路接通，不能据此认定云端已经完成或优化成功。
